适配器开发指南

交付和支付都被抽成了适配器。要接一个新的货源或支付通道，你只需要写一个文件、在注册表里加一行， 不需要动订单流程、不需要动前端。

一、交付适配器

交付适配器负责回答两个问题：这一单怎么发货？现在还剩多少货？

// src/adapters/delivery/my-supplier.js
module.exports = {
  name: 'my-supplier',

  // 出货。返回三种结果之一：
  //   { ok: true,  items: ['交付内容', ...], message: '...' }
  //   { ok: false, manual: true, message: '转入人工处理' }
  //   { ok: false, message: '失败原因' }
  async deliver(order, product, ctx) {
    const res = await fetch(product.deliveryConfig.url, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ sku: product.sku, qty: order.quantity }),
    });
    if (!res.ok) return { ok: false, message: `上游 HTTP ${res.status}` };
    const data = await res.json();
    return { ok: true, items: data.codes, message: '已由上游发货' };
  },

  // 剩余库存。返回 -1 表示未知或不限。
  stock(product) {
    return Number(product.deliveryConfig.stock ?? -1);
  },

  // 可选：后台「导入卡密」按钮会调用它
  async importKeys(product, keys) {
    const list = String(keys).split(/\r?\n/).filter(Boolean);
    // …写入你自己的存储…
    return { imported: list.length, skipped: 0, total: list.length };
  },
};

然后在 src/adapters/delivery/index.js 底部注册：

register('my-supplier', require('./my-supplier'));

商品侧只要在 config/products.json 里把 delivery 指向这个名字， 再填好 deliveryConfig 就行。

二、内置的三种交付方式

名称行为适用场景
pool 从 data/stock/ 下的文本文件里取号，取走即删除 你手上已经有一批卡密、兑换码、授权码
upstream 调用上游接口取货，支持请求体模板与响应取值路径 中间商模式：绑定供应商，由供应商履约
manual 付款后进人工队列，你在后台填交付内容 低频、需要人工核对、上游暂时没有接口

upstream 配置字段

字段说明
url上游发货接口地址
method默认 POST
headers请求头，通常放鉴权 token
body请求体。支持 {{qty}} {{orderId}} {{sku}} {{productId}} 占位符
itemsPath从响应里取交付内容的路径，例如 data.items
itemField当返回的是对象数组时，取哪个字段作为交付内容
timeoutMs超时毫秒数，默认 10000
stock声明库存；不填即为未知

三、支付适配器

// src/adapters/payment/my-gateway.js
module.exports = {
  name: 'my-gateway',
  label: (site) => '我的支付通道',

  async createPayment(order, ctx) {
    return { ok: true, payUrl: `https://pay.example.com/?out=${order.id}`, label: '我的支付通道' };
  },

  // 网关异步回调 POST /api/pay/webhook
  verifyCallback(payload, ctx) {
    // 自己验签，验过了就返回订单号
    return { ok: true, orderId: payload.orderId, amount: Number(payload.amount) };
  },

  // 可选：需要自己的回跳路由时实现它，路径前缀是 /api/pay//
  async handleRequest({ req, res, url, params, ctx }) {
    return false;
  },
};

同样在注册表里加一行，然后把 config/site.json 的 payment.driver 改成它。

四、内置的三种支付方式

名称行为
mock演示用：点开链接即视为付款成功。切勿对公网开放。
manual线下收款，由管理员在后台确认已收款
webhook通用网关：带 HMAC 签名跳转 + 回调验签

webhook 签名规则

跳转时携带 orderId、amount、currency、subject、 notifyUrl、sign，其中：
sign = HMAC-SHA256(secret, orderId + ":" + amount)

网关回调 POST /api/pay/webhook 时需要回传同样的字段，签名与金额都校验通过后订单才会发货。

五、订单状态机

pending        下单完成，等待支付
  ├─ expired   超过 config/site.json 的 order.expireMinutes 未支付
  ├─ failed    创建支付时出错
  └─ paid      收到款项
       ├─ delivered        交付成功，顾客可凭 token 取货
       └─ pending_manual   进入人工队列

六、部署要点

  • 正式环境务必设置 ADMIN_PASSWORD 与 APP_SECRET。
  • 把支付驱动从 mock 换成 manual 或 webhook。
  • 设置 PUBLIC_URL，否则支付回调地址会指向本机。
  • data/ 目录存的是订单和卡密，请挂载持久卷并排除在版本控制外。
  • 建议放在 Nginx / Caddy 后面处理 HTTPS，本服务本身只监听 HTTP。
